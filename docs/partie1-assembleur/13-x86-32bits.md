# x86 32 bits

!!! info "Chapitre d'approfondissement"
    Dernier chapitre de la partie 2. Le cours a tout appris en 64 bits, mais beaucoup de binaires réels restent en **32 bits** : vieux logiciels, nombreux malwares, et une bonne part des challenges CTF. Les différences sont assez marquées pour dérouter. Ce chapitre les présente, avec des désassemblages réels.

!!! note "Note sur l'environnement"
    Les exemples de ce chapitre sont de petits programmes NASM 32 bits complets, assemblés avec `nasm -f elf32` puis liés avec `ld -m elf_i386`, sans bibliothèque C : ils fonctionnent sur tout Linux x86-64. Pour écrire une fonction NASM, voir l'encadré du début du chapitre 9. L'image du laboratoire contient aussi `gcc-multilib` : `gcc -m32 prog.c -o prog` y compile directement un programme C en 32 bits, ce qui permet de comparer avec le désassemblage d'un vrai compilateur. Les appels système 32 bits passent par `int 0x80` (et non `syscall`), avec d'autres numéros.

## 13.1 Huit registres, en e...

Le mode 32 bits n'a que **huit** registres généraux, les versions `e` (*extended*) : `eax`, `ebx`, `ecx`, `edx`, `esi`, `edi`, `ebp`, `esp`. Pas de `r8`-`r15`, pas de registres 64 bits. Chacun fait 32 bits ; leurs moitiés basses (`ax`, `al`...) existent comme en 64 bits. Cette rareté de registres explique pourquoi le code 32 bits va bien plus souvent en mémoire (sur la pile) que le code 64 bits.

## 13.2 La convention d'appel cdecl

C'est le plus gros changement. En 32 bits (convention **cdecl**, la plus répandue sous Linux), **tous les arguments passent par la pile**, poussés de droite à gauche par l'appelant. Il n'y a pas de registres d'arguments. La valeur de retour reste dans `eax`.

Voici une fonction `int som(int a, int b)` appelée en poussant ses arguments, et son désassemblage 32 bits réel :

```asm
; appel : push 2 ; push 40 ; call som ; add esp, 8
som:
    push ebp
    mov  ebp, esp
    mov  eax, [ebp+8]    ; 1er argument (a)
    add  eax, [ebp+0xc]  ; 2e argument (b)
    pop  ebp
    ret
```

Après `push ebp` / `mov ebp,esp`, le cadre est en place et les arguments se lisent à **offsets positifs** par rapport à `ebp` :

| `[ebp]` | ancien `ebp` sauvegardé |
|---|---|
| `[ebp+4]` | adresse de retour |
| `[ebp+8]` | 1er argument |
| `[ebp+0xc]` (12) | 2e argument |
| `[ebp+0x10]` (16) | 3e argument... |

C'est la grande différence de lecture avec le 64 bits : en 32 bits, les arguments sont en `[ebp+8]`, `[ebp+12]`..., pas dans `rdi`, `rsi`...

## 13.3 Qui nettoie la pile

En cdecl, c'est **l'appelant** qui retire les arguments de la pile après le `call`, typiquement par un `add esp, N`. On le voit juste après chaque appel :

```asm
    push 2
    push 40
    call som
    add  esp, 8      ; cdecl : l'appelant nettoie (2 arguments * 4 octets)
```

Une autre convention, **stdcall** (fréquente dans l'API Windows), confie ce nettoyage à la fonction appelée, qui se termine alors par `ret 8` (un `ret` qui dépile aussi 8 octets d'arguments). Voir un `ret N` avec `N` non nul signale du stdcall. Distinguer les deux aide à identifier l'origine d'un binaire.

## 13.4 Pas de rip-relative : l'astuce call/pop

En 64 bits, on adresse les données par rapport à `rip` (`lea rsi, [rel msg]`). En 32 bits, **il n'existe pas d'adressage relatif au compteur de programme**. Pour écrire du code indépendant de la position (indispensable aux shellcodes), on récupère la valeur de `eip` par une astuce : un `call` pousse l'adresse de l'instruction suivante, qu'un `pop` récupère.

```asm
_start:
    call apres
    db   "32 bits!", 10   ; données placées juste après le call
apres:
    pop  ecx              ; ecx = adresse de la chaîne (poussée par call)
    ...
```

Le `call apres` pousse l'adresse des octets qui le suivent, c'est-à-dire la chaîne, puis saute à `apres` où `pop ecx` la récupère. Désassemblée, cette zone trompe `objdump`, qui prend la chaîne pour des instructions (du charabia après le `call`) : c'est un signe classique de données mêlées au code. Les compilateurs utilisent une variante nommée `__x86.get_pc_thunk` : une minuscule fonction qui fait `mov eax, [esp] ; ret` pour renvoyer l'adresse de retour, donc `eip`.

## 13.5 32 contre 64 bits en un coup d'oeil

La même fonction `som` compilée en 64 bits lit ses arguments dans les registres :

```asm
; som, 64 bits (gcc -O0)
mov [rbp-0x4], edi    ; a vient de edi
mov [rbp-0x8], esi    ; b vient de esi
...
```

| | 32 bits (cdecl) | 64 bits (System V) |
|---|---|---|
| Registres généraux | 8 (`eax`..`esp`) | 16 (`rax`..`r15`) |
| Arguments | sur la pile (`[ebp+8]`...) | registres `rdi, rsi, rdx, rcx, r8, r9` |
| Nettoyage pile | l'appelant (`add esp, N`) | pas nécessaire (registres) |
| Adressage données | astuce call/pop | relatif à `rip` |
| Appel système | `int 0x80` | `syscall` |

Repérer des `[ebp+8]` systématiques, un `add esp, N` après les appels, ou un `int 0x80`, signale immédiatement du 32 bits.

## Exercices gradués

Assembler le 32 bits avec `nasm -f elf32 f.asm -o f.o && ld -m elf_i386 f.o -o f`. Deux programmes complets servent de point de départ : [exemples/som32.asm](../exemples/som32.asm) (la fonction `som` et son appel, le résultat sert de code de retour, lisible avec `echo $?`) et [exemples/callpop32.asm](../exemples/callpop32.asm) (l'astuce call/pop de la section 13.4). Dans les deux, le programme se termine par l'appel système `exit` en 32 bits : numéro 1 dans `eax`, code de retour dans `ebx`, puis `int 0x80`.

**Exercice 13.1 (niveau 1)** Assembler et exécuter `som32.asm`, qui appelle la fonction `som` via la pile (section 13.2). Vérifier que `som(40, 2)` renvoie `42` (par le code de retour). À quels offsets de `ebp` la fonction lit-elle ses deux arguments ?

**Exercice 13.2 (niveau 2)** Modifier `som` pour qu'elle calcule `a - b` au lieu de `a + b`, en gardant la lecture des arguments sur la pile. Vérifier avec `50` et `8`.

!!! note "Contraintes"
    Lire les arguments en `[ebp+8]` et `[ebp+0xc]`, pas dans des registres : il n'y a pas de registres d'arguments en cdecl.

**Exercice 13.3 (niveau 2)** Dans le programme appelant, repérer l'instruction qui nettoie la pile après `call som`. Combien d'octets retire-t-elle et pourquoi ? Qu'aurait-on vu à la place en stdcall ?

**Exercice 13.4 (niveau 3)** Assembler `callpop32.asm`, l'exemple call/pop de la section 13.4, et vérifier qu'il affiche `32 bits!`. Dans le désassemblage, expliquer pourquoi `objdump` montre du charabia juste après le `call`, et comment l'adresse de la chaîne arrive dans `ecx`.

**Exercice 13.5 (niveau 2)** Comparer les désassemblages de `som` en 32 et 64 bits. Citer trois différences concrètes (d'où viennent les arguments, nombre de registres, qui nettoie la pile).

**Exercice 13.6 (niveau 3, lecture)** On lit dans une fonction 32 bits : des accès à `[ebp+8]`, `[ebp+0xc]` et `[ebp+0x10]`, et un résultat laissé dans `eax`. Combien d'arguments la fonction prend-elle, et où est sa valeur de retour ?
